# v1.25.0 — Shared context: learnings in the journal, project memory across runs

> **Status:** implemented — v1.25.0. Design date: 2026-09-18. Base: v1.24.0. Prompted by the
> replies to Anthropic's Claude Code Projects launch (2026-09-17) and a review of the
> `project-context` skill as the cross-run memory layer.

## What people said breaks with parallel agents

From 113 replies and quotes on the launch post, the substantive complaints:

- context passing between workers "is what always broke" in hand-rolled coordinator setups;
- workers redo or collide on each other's work because each knows only its own history — the
  fix that worked for one team: "make the shared state boring: one place that records what was
  already done, checked before acting instead of after";
- one bad assumption infects every thread and is hard to trace back;
- a plan change mid-run never reaches the coding thread;
- recovery must be idempotent — resuming after a tool error must not repeat side effects;
- cost multiplies by thread count; an unattended run has no local stop condition.

Projects answers with standing context (instructions, repositories, a memory folder any thread
writes) and a coordinator that "sees what threads report back, not every step they take".

## Where orchestrate stood (v1.24.0)

Coordination was solved, CLI-agnostically: exclusive `--owns`, `brief-check` write collisions,
`board peers`, `wait --task`, gated lanes, lineage mail, hash chain, idempotent resume, pinned
snapshots, decisions with ids. Two gaps were real:

1. **Knowledge was dark between dispatch and return.** A worker's discovery reached peers only
   after its report landed and the controller curated a field-guide line. Live evidence: two
   lanes each started the backend; hierarchical workers each re-derived orientation.
2. **Nothing survived the run.** `archive/<run-id>/` is dead storage.

## Options weighed

1. Status quo — frozen snapshot, controller relay. Drift-free; knowledge stays dark.
2. A worker observation event delivered through the existing piggyback — chosen.
3. A digest of record changes since dispatch on the same watermark — chosen.
4. Compose with `project-context` across runs, board prints the command — chosen.
5. Live/mid-turn propagation, per-worker mailboxes, vector memory, auto-summarisation,
   worker-side `ctx` — rejected: no CLI-agnostic interrupt exists; services and opaque ranking
   break the ethos; a linked worktree has no ledger.

## Decisions

- `learn` is an **observation**: `Learn` rides `load()` like `Mail`, never a candidate state,
  not in `TASK_EVENTS` (a learning after `finish` is not work). `LEARN_CAP` 3 per stint,
  `LEARN_LEN` 300, run-wide dedupe on a casefolded, whitespace-collapsed key.
- **Team scope**: `State.receives(agent, L)` — same dispatcher, the sender's lead, or the
  sender's own workers; the controller sees all. Cross-subtree spread is curation (field guide,
  later briefs), never automatic.
- **One watermark**: `State.digest()` = unread mail + unread learnings + record changes;
  `ack(upto=max seq)` covers all three, so a batch can never skip a mail. Record changes are
  decisions and rails with `seq > max(watermark, stint.seq)` — the brief snapshot predates them.
  The controller never receives changes (it wrote them).
- `board decide --why` stores the rationale; `Change.revised` is computed against journal-sourced
  decisions only (the `decisions.md` mirror is not a prior).
- `BOARD_AGENT` defaults every worker-side `--agent`/`--from` inside a launched lane.
- `board memory` is a **view**: a `project-context` v1 record built from the journal and
  workspace; empty sections stripped, `scope` kept (required, `[]` = project-wide). Rationale
  never invented: "not recorded during the run (board decide --why); journal seq N".
- **No dependency**: `project_memory(ws)` only detects `.agent/project-context.json` or
  `.agent/PROJECT_CONTEXT.jsonl` at the repo root; hints are printed at `init`, `finish` and
  `resume`; the board never runs `ctx`. Workers never run `ctx`.

## What project-context contributed

Typed `attempts` with outcomes (the query "don't redo what failed"), `learnings` with type and
confidence, `supersedes` semantics, scope/path retrieval under a token budget, `task.id` and
`agent.session_id` to link a run's entries. Not adopted in-run: rich narrative records — reports
carry depth; a worker writing 300-word observations mid-task is the chatter the caps exist to stop.
No change was needed in `project-context` itself; two notes for its backlog: warn when `ctx append`
runs in a linked worktree with storage `repo`, and a per-session recall filter.

## What no system solves

A wrong decision by the coordinator still reaches every worker. The defences are traceability
(ids, journal, `(revised)` in the digest) and the independent fresh-context final gate — both kept.
