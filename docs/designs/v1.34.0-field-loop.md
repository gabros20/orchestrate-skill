# v1.34.0 — the field loop: every run is data for the skill

> **Status:** implemented — v1.34.0, 2026-10-31.

## Problem

`orchestrate` had static evals only. Real runs journaled rich evidence (gates, checks, receipts,
learnings, finishes, each event stamped with the release), but nothing turned that evidence into a
signal for the next release. The v1.33 fixes came from mining fourteen transcripts by hand. Research
(`docs/research/2026-10-skill-rl/`) found two constraints:

- **Text-space optimization needs gated, bounded edits.** SkillOpt, GEPA, EvoSkill and Hermes all
  work this way.
- **A pass/fail score is drowned in run-to-run noise at our run counts.** "Skill Issue" found
  GEPA's +4.9 points indistinguishable from variance.

So the first step is denser signal from every run, plus a channel back to the repo.

## Decisions

- **`board score`, deterministic and versioned.** Groups are ordered by role in the loop:
  - outcome, cost and calibration are the targets;
  - quality, discipline, communication and friction explain them.

  Optimizing a process metric is Goodhart's law: "fewer gate rounds" is also what a lenient
  reviewer produces.
- **Calibration as the dense signal** (RLCR, arXiv 2507.16806, without weights): `Confidence:` on
  implementer reports and reviewer verdicts, scored by Brier and bias against later truth:
  - **A return** is wrong when its attempt's gate or check fails afterwards, or a new attempt
    starts. It is right when the task reaches the ledger.
  - **A pass verdict** is wrong when a later check on the task, or a later gate of its kind, fails.
  - **Fail verdicts are not scored.** They resolve trivially.

  **The board reads the line from the file**, so no agent has to remember a flag. The tool beats
  prose here; AHE's ablation found the same.
- **Friction is outside the journal.** `raw/friction.jsonl` keeps the journal semantic. The hook
  wraps `main()`, so the selftest exercises it. The observer never fails the command it observes.
- **`board retro` lists candidates, and the controller sorts them.** The board cannot tell a
  project's lesson from a skill's flaw, so retro shows signals with evidence. The controller judges
  ("would it recur in another repo on this release?") and drafts only skill-level findings, each
  with a metric and a predicted direction (AHE's falsifiable edit contract). A report without a
  prediction cannot be checked later.
- **Filing is outward-facing.** The draft lives in `.orchestrate/retro/`. Dedupe goes through
  `gh issue list`, and `gh issue create` runs only on the user's yes. The board prints both lines
  and never runs them.
- **The retro is a reference read at finish only** (`shared-retro.md`). It costs nothing until
  then. One SKILL step-7 sentence and one table row point to it.

## Next phases (v1.35.0: `bench/` and `orchestrate-evolve` — see `bench/README.md`)

  It needs a budget decision first.
- **Executable decision replays** for `evals/output/`.
- **A maintainer `orchestrate-evolve` skill:** bounded edits, a rejected-edit ledger, and
  prediction checks against field data.
- **ACE counters on learnings.**
