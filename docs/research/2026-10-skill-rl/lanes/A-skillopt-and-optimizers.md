# Lane A: SkillOpt and the skill/prompt-optimization ecosystem

Date: 2026-10-30. Grades: **repo-read** (I read code/README/docs in the repo), **docs** (paper abstract or official docs page read), **post-only** (secondhand or not verified). SkillOpt commit read: `bc0a392` (v0.2.0 line).

## 1. Microsoft SkillOpt (https://github.com/microsoft/SkillOpt, paper arXiv 2605.23904)

**Thesis (repo-read, README + docs/guide/training-loop.md).** The skill Markdown is the trainable state of a frozen agent. Edits to it are trained like weights: epochs, minibatches, a textual "learning rate" (max edits per step), a validation gate. Deployed artifact is one `best_skill.md` (300-2,000 tokens), zero extra inference calls.

**Loop (repo-read: `skillopt/engine/trainer.py`, `docs/guide/training-loop.md`).**
1. Rollout: target agent runs a train minibatch with the current skill; env adapter returns trajectory + score (hard exact-match and soft partial score).
2. Reflect: an *optimizer* model reads minibatches of 8 trajectories (failures always, successes optionally; `gradient.failure_only`) using `skillopt/prompts/analyst_error.md` / `analyst_success.md`. Output is strict JSON: `failure_summary[]` plus `patch.edits[]` with ops `append | insert_after | replace | delete`, each anchored on exact target text, "AT MOST L edits", "generalizable, no task-specific values", "do not duplicate existing content".
3. Aggregate: hierarchical merge of semantically similar patches (`gradient/aggregate.py`, `merge_*.md`).
4. Select/clip: rank edits, keep top-k where k = learning rate (default 4, cosine-decayed to min 2) (`optimizer/clip.py`, `scheduler.py`, configs/_base_/default.yaml).
5. Update: apply patch (mode `patch | rewrite_from_suggestions | full_rewrite_minibatch`).
6. Gate (`evaluation/gate.py`): candidate re-run on a held-out *selection split*; accepted only if score is **strictly higher** than current. Metric `hard | soft | mixed`; soft/mixed exist because small selection sets are insensitive. Optional "semantic density" penalty on directive words (MUST/NEVER/...) to stop shouty bloat.
7. Rejected-edit buffer: rejected edits plus before/after scores are fed back as context to later reflection in the epoch (`_format_step_buffer`).
8. Epoch boundary: *slow update* re-rolls previous-epoch and current skill on the same samples, buckets items improved / regressed / persistent-fail / stable-success, writes protected guidance between `<!-- SLOW_UPDATE_START/END -->` markers (analysts are told never to edit that region). *Meta-skill* = cross-epoch strategy memory fed to later reflections.

**Defaults (repo-read):** 4 epochs, batch 40, minibatch 8, 16 analyst workers, seed 42, deterministic batch seeds (`make_base_seeds`), splits train/val/test with fixed `split_seed`. Final report separates validation-best snapshot from last-current.

**Results (docs: README + abstract).** 6 benchmarks (SearchQA, OfficeQA, SpreadsheetBench, ALFWorld, DocVQA, LiveMathematicianBench), 7 target models, 3 harnesses (chat, Codex CLI, Claude Code CLI). Claims best-or-tied on 52/52 cells, beating human, one-shot LLM, Trace2Skill, TextGrad, GEPA, EvoSkill skills. GPT-5.5: +23.5 (chat), +24.8 (Codex), +19.1 (Claude Code) points. Skills transfer across model scale and Codex<->Claude Code. All numbers are the authors' own; single seed noted in Sleep results.

**Benchmark/eval harness contract (repo-read: docs/guide/new-benchmark.md).** A benchmark is ~200 lines: a `SplitDataLoader` (train/val/test item dicts with `id`, `ground_truth`, `task_type`), a rollout helper that scores each item and persists the per-item conversation, an `EnvAdapter`, a YAML config, and an optional `skills/initial.md`. Scorers are real, deterministic evaluators: SQuAD EM, multiple choice, and for SpreadsheetBench the agent's generated openpyxl code is *executed* and the output workbook diffed cell-by-cell against a golden file. Exec backends (`codex_exec`, `claude_code_exec`, `cursor_exec`, `copilot_exec`) run real agent CLIs as the target; `claude_trace_to_optimizer: true` feeds the CLI's trace to the optimizer.

**SkillOpt-Sleep (repo-read: docs/sleep/README.md, RESULTS.md).** The deployment-time variant, closest in spirit to what the user wants: harvest local Claude Code/Codex/Copilot/Cursor transcripts -> mine recurring tasks with checks (`rule` judge: regex/section_present; `exact`; `rubric`) -> replay on own budget -> reflect/bounded edit -> gate on held-out replays -> *stage a proposal for human adoption*. Key design points:
- `gate_no_regression: true` forces every validation task to preserve-or-improve, not just the mean. Per-task deltas are logged.
- Evidence log `evidence.jsonl` of redacted prompts/replies; secrets redaction is "defense in depth".
- **Optimizer-feedback boundary**: the optimizer sees `optimizer_feedback` (a semantic description of the check), never the raw regex/judge rationale, to stop learning to imitate the verifier. Non-rule judges fall back to a generic message (fail-closed).
- Evidence the gate matters (RESULTS.md): GPT-5.4-nano/SearchQA, ungated 0.554 -> 0.026 over 5 nights (optimizer learned "answer with title string verbatim"); gated twin rejected all of those edits, 0.570 -> 0.570. Gated gains: nano +11.9 pts, GPT-5.5 +6.0 pts; recall of relevant past experience (k=10-20) captures most of full-history replay's gain at lower cost. Sensitivity sweep: more rollouts/nights/per-night tasks *reduced* gain. Single seed.

**Cost per iteration (inference, not stated):** a step = batch of 40 rollouts + ~5 analyst calls + merge + selection-set re-eval of the candidate. For a coding-agent target a "rollout" is a full agent run, so this is dominated by rollout count, not optimizer tokens. Not feasible per-edit for a multi-hour app build; feasible only with a small deterministic task set.

## 4. Cross-cutting synthesis

1. **Every credible loop has the same shape**: deterministic task set with a verifier -> run N times -> separate train (reflection) from held-out (accept) -> bounded, anchored, small edit -> accept only on strict improvement -> keep rejected edits as negative memory. SkillOpt, EvoSkill, skill-creator's description loop and Hermes all do this.
2. **Regression guards in order of strength**: per-task no-regression gate (Sleep `gate_no_regression`) > Pareto frontier (GEPA, EvoSkill) > mean-improvement on held-out (SkillOpt) > human review of a staged proposal (Sleep, Hermes) > nothing (DC, ACE). Ungated optimizers demonstrably collapse (Sleep: -52.8 pts).
3. **Noise is the dominant problem for coding-agent targets.** Agent Lightning Skill and skill-creator both say: repeat runs, report stddev, treat "unavailable measurement" as unknown, hold scorer and eval contract fixed. SkillOpt's strict `>` on a tiny selection set is fragile for stochastic multi-hour runs.
4. **What to edit matters**: AHE ablation (tools/middleware/memory beat prompt prose) and SkillsBench (focused <=3-module skills beat bundles) both argue for editing the *CLI and structured gates* more than adding prose to SKILL.md. SkillLens warns model-generated skills can transfer negatively.
5. **Judge leakage is a real failure mode** (Sleep's optimizer-feedback boundary). For orchestrate, the verifier (hidden tests) must never be quoted into skill text.
6. **Falsifiable edits** (AHE): each proposed change predicts which tasks flip; a later run checks it. Cheap to adopt, adds attribution that none of the others have.

## 5. Transferable to orchestrate (ranked)

Orchestrate's asset: a hash-chained journal of dispatch/return/gate/check/mail/learn/token/finish events. That is a ready-made, structured "trace" (better than AHE's 10M-token raw dumps), so the Debugger step is a `board` subcommand rather than an LLM summariser.

1. **Paired, deterministic-verifier benchmark (SkillsBench/Terminal-Bench pattern)** · Task = small app spec + `verifier/test.sh` (hidden pytest/Playwright acceptance, writes scalar reward) + oracle; run `with orchestrate vN` vs `baseline` (no skill, or previous release snapshot) · Why: it is the only thing that detects regression/improvement for a harness whose evals are static today; skill-creator already prescribes the same-turn A/B and snapshot baseline · Cost: authoring 3-5 tasks (~days); each run = one full build (likely tens of dollars, hours), so budget ~3 repeats x 3 tasks x 2 arms per candidate.
2. **Score vector from the journal, not a single scalar** · reward (hidden tests) + `board exec` exit codes/durations + review-gate pass/fail counts + rework count + token receipts + wall time + finish status, emitted by a `board score` command · Why: SkillsBench/skill-creator report pass rate with time and tokens; Pareto/no-regression needs per-dimension numbers; the journal already records them and its hash chain makes scores tamper-evident · Cost: one script, no model calls.
3. **Acceptance rule = no-regression + variance-aware** · accept a skill edit only if hidden-test pass rate does not drop on any task and mean improves, using >=3 repeats and reporting stddev; unknown/failed measurement = reject (Sleep `gate_no_regression`, Agent Lightning Skill guidance, GEPA Pareto) · Why: SkillOpt's strict-greater on a small noisy set would accept lucky draws · Cost: multiplies run cost by repeats; mitigate with a cheap first stage (static evals + one task) before full runs.
4. **Falsifiable proposal contract (AHE)** · every proposed edit/issue carries failure evidence (journal event ids), root cause, targeted fix, predicted effect on named metrics/tasks; next benchmark run auto-checks predictions and flags edits whose prediction failed · Why: gives attribution across incremental versions, and fits the planned issue-proposing sub-skill directly · Cost: a schema + a check script.
5. **Journal digester as the "Agent Debugger"** · `board digest --run` yields a layered report (overview of gates failed, retries, longest `exec`, mail stalls, token hot spots) with event-id links so the reflector can drill down · Why: AHE shows distilled-with-provenance beats raw traces; orchestrate already has structured events so this is mostly deterministic code · Cost: low; the reflection call is one LLM pass per run.
6. **Staged human-adopted proposals, never auto-merge (Sleep, Hermes)** · optimizer output = candidate diff on a branch + GitHub issue draft with benchmark deltas; human adopts · Why: the user's request (3) is exactly this; both Sleep and Hermes made it the default after the collapse result · Cost: low.
7. **Bounded anchored edits + rejected-edit buffer + protected regions** · cap edits per candidate (SkillOpt lr 2-4), anchor with exact text, store rejected edits with scores in a file (EvoSkill `feedback_history.md`, SkillOpt step buffer), mark human-owned invariants (CLAUDE.md "specialized invariants") as protected like `SLOW_UPDATE` markers · Why: prevents context collapse (ACE), keeps `scripts/check-sync` invariants intact · Cost: tiny.
8. **Prefer editing `board` and gates over prose** · AHE ablation and SkillsBench "focused skill" findings; target candidate edits at CLI behaviors (new checks, defaults, hold rules) and SKILL.md *compression*, using the existing compression-ablation eval · Why: evidence says prose edits transfer worst · Cost: neutral.
9. **Optimizer/verifier separation** · optimizer sees metric descriptions, never hidden test source; benchmark tests live outside the repo the agent builds in (Sleep feedback boundary; Agent Lightning "scorer immutable") · Cost: directory discipline.
10. **Cheap proxy tier: skill-creator style description/trigger and traversal loops with 60/40 split** · use for routing/description changes only; already close to the existing activation evals · Cost: low.
11. **Playbook deltas from `board learn` (ACE curator)** · learnings become helpful/harmful-counted deltas, pruned by outcome across runs · Why: orchestrate already stores learnings; counters tie them to benchmark outcomes · Cost: moderate; do after 1-5.

**Do not adopt**: Agent Lightning RL training (weights), ungated Dynamic-Cheatsheet-style online self-edit, full-rewrite optimizers, LLM-only rubric judging as the sole reward (darwin cites 46.4% self-eval accuracy; DevBench uses judges only for design artifacts), per-edit SkillOpt-scale rollouts (too many full builds).
