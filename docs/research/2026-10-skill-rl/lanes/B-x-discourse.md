## Finalists

### A. Skill and prompt optimization (the closest match to the user's goal)

1. **SkillOpt** - @Yif_Yang, 2026-05-25, 858 / 1250, https://x.com/Yif_Yang/status/2058918317918998795. Treats a natural-language skill as a trainable parameter with text-space analogues of learning rate, mini-batch, schedule, momentum, a rejected-edit buffer and slow/meta updates. Claims best or tied-best in 52/52 settings, 6 benchmarks, 7 models, direct calls plus real Codex and Claude Code loops. Overfitting answer in thread: train / validation / test have no overlap; for SearchQA the split is 2:1:7, so 70% is held out and all reported numbers are held-out. Code link in thread. Author says first paper title was "Skill as LoRA".
2. **SkillOpt lessons thread** - @muratcan (maintains a context-engineering skills repo), 2026-05-26, 2274 / 5001, https://x.com/muratcan/status/2059113412278227328. The most useful single post for this project. His distillation of the paper: (a) the validation gate is the only thing that matters; held-out set, strict improvement, ties rejected; best skills end with only 1 to 4 accepted edits, so "if your loop accepts most proposals you are shipping slop"; (b) bounded edits (4 to 8 per step) beat rewrites, and removing the budget collapses performance, so cap diff size; (c) compactness wins, median final skill about 920 tokens; (d) a Codex-trained skill ported to Claude Code gained +59.7 points on SpreadsheetBench, so the skill matters more than the harness; (e) a small model plus an optimized skill approximates frontier behaviour on procedural tasks; (f) **verification is the bottleneck**, because every gate needs an auto-grader and open-ended work lacks one. His own shipping lessons: skill description and body are separate surfaces that can silently disagree (only end-to-end task tests catch it), and **aggregate accuracy is the wrong unit** (rewriting three descriptions moved the corpus average about 1pp while individual cases swung). He positions SkillOpt against GEPA/TextGrad: GEPA does reflective evolution with Pareto selection but no bounded learning rate.
3. **SkillsBench** - @xdotli, 2026-01-05, 291 / 219, https://x.com/xdotli/status/2008106947317506500. Announced as the first benchmark of whether skills improve agent performance and how well agents use them; open call for task contributors. Replies point at Letta's context-bench (skills on a live leaderboard since Nov). Thread has no results; I could not confirm the headline findings from X alone. Check the repo before citing.
4. **Vercel skills-vs-AGENTS.md eval, via @muratcan** - 2026-01-29, 1111 / 1291, https://x.com/muratcan/status/2016684758588154239. Next.js 16 API eval: baseline 53%, skill default 53%, skill with explicit instructions 79%, 8 KB compressed docs index in AGENTS.md 100%. In 56% of eval cases the skill was never invoked. "You MUST invoke the skill" hurt (agent read docs first, missed project context); "explore project first, then invoke" did better. Same skill, different prompting, different outcome. Relevance: a skill's measured gain depends on trigger wording, so a benchmark must score invocation as well as outcome.
5. **Hermes self-evolution with GEPA** - @RajaPatnaik summarizing NousResearch, 2026-04-07, 463 / 565, https://x.com/RajaPatnaik/status/2041305017781833859 (also in the user's bookmarks). Pipeline: read skill, generate eval set, run DSPy+GEPA over execution traces, produce candidate variants, check guardrails, **submit best variant as a PR with human review**. Cost claimed $2-10 per run. Guardrails: full test suite must pass, size limits, semantic-drift check, caching-compatibility check. Phase 1 is skills only; tool descriptions, system prompts and code are planned. Direct template for "skill proposes PRs/issues against itself".
6. **GEPA** - @JacksonAtkinsX 2025-07-28 (1856 / 2027), @lateinteraction 2025-07-28 (484 / 351): "Reflective Prompt Evolution Can Outperform GRPO" (UC Berkeley, Stanford, Databricks). Reflect on traces in natural language, evolve prompts on a Pareto frontier; claims up to 35x fewer rollouts than RL. Pre-2026 and outside the date window; included because it is the reference method everyone else compares to. Post-only.
7. **Agentic Context Engineering (ACE)** - @omarsar0 2025-10-10 (1120 / 1338), https://x.com/omarsar0/status/1976746822204113072. Treat prompts and memory as a living playbook: log trajectories, reflect into actionable bullets (strategies, tool schemas, failure modes), merge as **append-only deltas with periodic semantic de-dupe**, use execution signals and unit tests as supervision, warm up offline then continue online. Related posts name failure modes ACE is built against: brevity bias and context collapse (iterative rewrites degrade into vague summaries). Directly relevant to a "learnings" journal that grows.
8. **Training-Free GRPO** - @rryssf 2025-10-15 (3534 / 3853), @akshay_pachaar 2026-02-16 (452 / 480). Tencent paper: no weight updates, learn from rollouts by comparing group attempts and distilling an experience library; claims about 100 examples and about $18 versus $10,000 for RL. Hype register ("killed fine-tuning"); treat as the weak, cheap version of the idea. Post-only.
9. **SkillOpt-style loops by individuals** - @SatyKrish reply in the SkillOpt thread: Karpathy-autoresearch-style loop over SKILL.md with fixed training sections, an LLM judge scoring a per-skill rubric, keep or revert on aggregate score, experiment log on a dedicated git branch. @cjzafir (2026-08-04, 653 / 1165) ships a local "tuned-skills" loop claiming +15-20%. @Chris_Worsey (2026-03-11, 3930 / 7882, https://x.com/Chris_Worsey/status/2031821234795659717): prompts as weights, Sharpe as loss, worst agent's prompt rewritten, keep or revert; 378 iterations, 54 modifications, 16 survived (about 30% acceptance). Replies (@swyx, others) immediately flagged hindsight bias and that the reported return is a backtest.

## Synthesis for orchestrate

**What is practical now.** The rich journal is the asset. The consistent pattern across SkillOpt, GEPA, ACE, Hermes self-evolution and Harness^2 is: run, collect traces, reflect in natural language, propose a bounded text edit, gate on held-out evidence, keep or revert, and put a human at the PR. orchestrate already emits the trace (dispatch, return, review gate, check exit, learning, token receipt), so the cheap steps are:
1. **Bounded edits only.** Cap a proposal to a few edits per SKILL/strategy file (SkillOpt's 4 to 8 per step; ACE append-only deltas with de-dupe). Keep a rejected-edit buffer so the same idea is not re-proposed.
2. **Strict gate with ties rejected**, on tasks not used to derive the edit. Expect low acceptance (SkillOpt: 1 to 4 accepted edits total; Chris_Worsey: 16 of 54).
3. **Post-run analyser as proposer, not actor.** Reflector reads the journal and emits issues/PRs (Hermes pattern: PR with test suite, size limit, drift check, human review). This matches the user's sub-skill idea and is the lowest-risk first step; it needs no benchmark to be useful, only to be validated.
4. **Mine journals and past sessions for a task set** (@ibragim_bad, @mihail_eric): the user's own corrections are the most realistic test cases.
5. **Score per task and per item, not only average** (@muratcan; Eric Zakariasson's per-task token metric). Track invocation as well as outcome (Vercel: skill never invoked in 56% of cases).
6. **Persist insights, not just scores** (Hyperagents' emergent memory; ACE playbook bullets). The `board learn` / board memory features fit.
7. **Budget metric**: tokens weighted by billing type per completed task; do not instruct the model to save tokens.

**What practitioners warn about.**
- *Overfitting to the bench:* SkillOpt answers with a three-way split (train / validation / test, test untouched). With a single small app benchmark there is little to hold out, so rotate several apps and keep a never-optimized final set. Hindsight bias in Worsey's thread (backtest) is the cautionary tale.
- *Verifier is the bottleneck:* @muratcan, @omarsar0 ("agents are bad at generating evals"). An app-build task needs executable acceptance tests written before the run and hidden from the agent, plus a rubric judge for the non-testable parts.
- *Reward hacking and leakage:* models fetch solutions from git history or the web (Cursor, Vals); Anthropic's checklist suggests hidden tests, impossible-task canaries, and a pro/anti-hack prompt differential. For orchestrate, the analogue is orchestrators that satisfy their own review gate or exit-code check without real verification; compare gate verdicts against hidden tests.
- *Judge noise:* calibrate LLM judges against humans, use rubrics with specific yes/no items (Mastra-style "7 of 11 criteria"), and expect that aggregate shifts of about 1pp are noise.
- *Scaffold dominates:* same weights 62% versus 33% by harness (Delangue). Pin harness version, model, effort and tool set in every benchmark record, or deltas are meaningless.
- *Variance:* none of the posts gave a seed or repeat protocol for agent runs; this is a gap. Repeat each cell k times and report spread before attributing a change to a skill edit. (Not backed by a post; my inference.)
- *Cost:* GEPA and Hermes claim $2-10 per optimization run, but a full app build per candidate is far more; budget the number of benchmark runs per skill change and prefer replaying journals offline for cheap pre-screening.
- *Length creep and collapse:* compact skills win (about 920 tokens median); iterative rewrites lose detail (ACE context collapse, brevity bias).
- *Orchestration is not free:* the "one agent with skills often beats multi-agent" claim means the benchmark needs a single-agent baseline arm to prove orchestrate's value.

**What is not worth copying.** Weight-training approaches (RLCR, harness-as-RL-environment, GRPO variants) need open models and GPUs; only their evaluation insights transfer. Hype threads ("killed fine-tuning", "95% of Anthropic engineers") carry no data.
